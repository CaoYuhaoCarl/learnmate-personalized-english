# 决策记录 - 教师校对与定稿

> 阶段: 待教师验收；整体结果: 软件验证通过，教学验收证据不足
> 更新: 2026-11-06（Asia/Shanghai）；同步: 实现、自动化测试、浏览器校对与真实 PDF 验证已完成。

## 目标、验收与边界

用户希望教师能修正模型识别错误、调整不合理评分，并自定义生成结果的内容（E1）。
推荐以现有教师 Web 为入口，在 AI 草稿完成后、正式报告导出前增加校对和定稿。
原项目的 [长期学生理解决策](../../../learnmate-personalized-english/decision.md) 已记录教师审核后交付的选择；本主题只细化本次作业的编辑与交付，不扩大到长期画像或学生端。
该关联文件位于另一工作区，仅供本地追溯；本记录中的设计不依赖该文件才能理解或实现。
用户已指示“开始执行设计”，授权按本记录实现与验证教师校对功能（E7）。
Agent 负责代码核验与建议，老师负责识别忠实性、判分合理性和最终内容验收。

实现验收标准 v1：

- 使用合成作业验证识别更正、增删误判或漏判错题、评分调整和评语修改均能保存，刷新或服务重启不丢失。
- 识别更正后，依赖它的判断明确等待复核；误判错题删除后，关联练习重点不再保留，相关分数建议按规则更新。
- 教师评分与系统建议分开保存，总分等于最终维度分之和；老师已修改的内容不被后台结果静默覆盖。
- 页面、正式 PDF 和结构化导出来自同一个已确认版本；旧版本不能冒充当前版本，导出失败可独立重试且不丢编辑。
- 两个浏览器标签页提交旧版本时得到冲突提示，不覆盖新修改；保存失败不得显示已保存。
- 老师用一份合成样例核对原图、修订结果和最终 PDF，确认系统忠实保留教师决定；软件测试不代替教学评价。

候选比较：直接修改 Markdown/PDF 操作直观，但会与页面、评分依据和结构化结果分离，不能完整满足 E1。
每次先确认识别再让模型开始分析可以减少错误传播，但会给所有作业增加等待步骤；首版推荐统一校对页，保留未来按需要拆分的可能。
推荐假设为沿用当前单老师本地应用和现有评分量表；若出现多人共同批阅或新的量表需求，再独立评估权限与评分配置。

## 建议交互与数据规则

流程：上传 → AI 处理 → 待校对草稿 → 教师确认 → 正式报告导出。
处理完成只表示草稿已生成，不等于教师确认。
作业内容无误时，老师可以直接确认，不必为了定稿做一次无意义修改。

桌面布局左侧显示原图并支持放大、切换图片，右侧依次显示识别内容、错题与建议答案、评分与评语、练习重点；手机按同一顺序排列。
底部提供“保存草稿”和“确认并生成 PDF”，显示未保存、保存中、保存失败和已保存状态。
常规修改用字段表单完成，保留“查看 AI 原稿”和字段修改标记，不引入整页富文本排版。
每个上传项分配稳定标识并关联保留的原图，不能依靠可能被重命名的文件名或聚合列表序号定位编辑对象。
一批有多份作业时按作业校对；确认本批报告前明确列出尚未校对和处理失败的项目。

“识别原文”只用于忠实还原学生实际写下的内容，学生本身的错误留在原答案中，教师建议写入纠正字段。
语法练习和作文错误均允许添加漏识别项、删除误判项、修改原答案或错误片段、建议答案与解释。
评分显示系统建议和教师最终分，教师调整维度分后自动求总分，可附简短原因；不另设容易与维度之和冲突的独立总分。
服务端校验分值范围与内容长度，不能仅靠浏览器输入控件校验。

修改识别文字不等于已经重新判断语言错误或文章结构。
此类修改将相关错题、评分、评语和练习重点标为待复核；首版允许老师直接修正并确认，不在每次保存时调用模型。
修改确定性证据，如错误列表、要点覆盖数量或结构判定，则重新计算系统评分建议与关联练习重点。
教师调整分数仍单独保留；若依据再次变化，显示新建议和原教师分并要求复核，不能静默替换。
练习重点通过稳定的证据标识关联错题，删除误判时同步撤销其派生建议，避免重复保存两份可独立编辑却互相冲突的事实。
如后续加入“基于修正内容重新分析”，只生成待采用的建议，接收教师修正文本作为依据，检查起始版本并保留教师修改。

每份作业保存初始提取、当前教师修订、确认快照三个明确来源，记录版本、修改时间及必要的修改来源。
当前共用 teacher 账号只能标明教师端修改，不能据此声称能区分具体老师。
处理状态和校对状态分离；确认内容版本与 PDF 导出状态也分离，PDF 失败不会撤销已保存的确认结果。
再次编辑已确认内容时保留旧定稿，界面明确显示新草稿尚未定稿，旧 PDF 标注版本和时间。
正式下载入口、历史报告列表、预览和结构化导出都必须使用同一确认版本；若提供草稿预览，应明确标为草稿。
写入携带基础版本并原子保存，过期版本返回冲突；导出绑定快照版本，可重试且不能覆盖其他版本。

## 实现落点与兼容

- `workflow.py` / `schemas.py`：保留每份作文的 `WritingEvidence`、分类结果和原图关联；当前持久结果不足以恢复完整评分依据。
- `submission_runner.py`：将“生成草稿”和“导出确认版本”拆开，复用原有确定性计算及报告生成函数。
- `submissions.py` / `web_app.py`：增加草稿保存、确认、版本校验、原图鉴权读取与导出重试，沿用现有存储与登录方式。
- `static/teacher.*`：在现有结果页面增加校对表单、对照原图、保存反馈、待复核提示和定稿动作。
- 旧提交缺少完整原始证据时明确标为历史结果，允许修订已有反馈并形成新版本；不能从旧总分反推出完整证据，也不能假称可完整重算。
- 保持既有 ADK 路径兼容；本设计首先应用于教师 Web，旧流程产出的报告不能自动标为教师已确认。

## 证据、评估与变更

- E1（用户需求，2026-11-06）：用户提出识别可能有误、评分不合理，需要人工老师介入编辑生成结果，并询问环节与设计。
- E2（代码事实）：`submission_runner.py:78-95` 聚合后立即调用 `write_report`；`web_app.py:224-257` 当前提供提交、查询与 PDF 读取，没有修订或确认接口。
- E3（代码事实）：`utils.py:359-416` 从内容覆盖、结构布尔值、语法与拼写错误数量和书写清晰度计算四项分数，再相加得到 20 分制总分；LLM 提供证据，程序给出分数。
- E4（代码事实）：`utils.py:468-557` 从错误与训练重点派生 `LearningNeed`；`workflow.py:222-251` 把作文证据转成反馈后，没有在返回结果中保留完整 `WritingEvidence`。
- E5（代码事实）：`schemas.py:71-170` 的作文原始证据含评分所需字段，当前持久化 `StudentLearningProfile` 只保留部分结果；语法提取只保留错题，不能据此计算完整正确率。
- E6（代码事实）：`static/teacher.js:154-216` 渲染只读结果；`submissions.py` 将状态及聚合结果写入任务目录，尚无教师版本与确认快照。
